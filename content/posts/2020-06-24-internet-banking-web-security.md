## 1. 서론

과거 국내 금융 사이트의 보안 프로그램은 Windows 중심으로 개발되어 Linux 등 다른 운영체제에서는 금융 서비스를 이용하기 어려운 경우가 많았다. 다양한 운영체제와 브라우저를 지원하는 웹 기반 뱅킹 서비스는 이러한 접근성 문제를 개선하는 방향으로 발전하였다.

이 글에서는 은행별 웹뱅킹 호환성과 금융 웹 애플리케이션에서 발생할 수 있는 취약점 및 대응 방안을 살펴본다. 여기서 다루는 운영체제·브라우저 호환성 중심의 웹뱅킹은, 금융기관의 조회·이체 기능을 API로 개방하는 오픈뱅킹 공동망과 구분한다.

## 3. 주요 웹 취약점

### 1) Brute Force

Brute Force는 가능한 비밀번호 조합을 반복적으로 대입하여 인증을 통과하려는 공격이다. 사전에 있는 후보를 대입하는 사전 공격도 반복적인 비밀번호 추측 방식에 포함된다.

금융 서비스의 로그인 페이지에서도 반복적인 인증 시도를 통제하지 않으면 계정 탈취 위험이 커질 수 있다. 비밀번호의 길이와 예측 가능성뿐 아니라 서비스의 시도 제한 여부도 중요하다.

### 2) SQL Injection

SQL Injection은 사용자 입력이 SQL 명령의 일부로 해석되어, 개발자가 의도하지 않은 데이터베이스 조회나 변경이 이루어지는 취약점이다. 사용자 입력을 문자열로 이어 붙여 쿼리를 구성하는 구현 등이 원인이 될 수 있다.

단순히 방화벽의 필터링 문제로만 볼 수는 없다. 핵심은 애플리케이션에서 쿼리의 코드와 입력 데이터를 안전하게 분리하는 것이다. 데이터베이스를 사용한다는 사실만으로 모든 사이트가 이 취약점을 가진다고 단정할 수는 없다.

### 3) XSS

XSS(Cross-Site Scripting)는 신뢰할 수 없는 입력이 웹페이지에서 실행 가능한 콘텐츠로 처리되어, 사용자의 브라우저에서 공격자가 의도한 스크립트가 실행되는 취약점이다.

세션 악용, 사용자 정보 유출이나 화면 변조로 이어질 수 있다. 입력 폼뿐 아니라 URL과 DOM 처리 등 여러 경로에서 발생할 수 있으며, `<script>` 태그만 차단하는 것으로 충분하지 않다.

### 4) CSRF

CSRF(Cross-Site Request Forgery)는 로그인된 사용자의 브라우저가 공격자가 의도한 요청을 대상 사이트에 보내도록 유도하는 공격이다. 서버가 요청의 출처와 의도를 검증하지 않고 자동으로 전달된 인증정보만 신뢰할 때 문제가 될 수 있다.

사용자 의도와 무관한 정보 수정·삭제·등록 요청 등이 이루어질 수 있다. XSS와는 서로 다른 취약점이며, CSRF가 반드시 스크립트 주입을 필요로 하는 것은 아니다.

### 5) RFI

RFI(Remote File Inclusion)는 웹 애플리케이션이 신뢰할 수 없는 입력을 이용해 원격 파일을 포함하는 취약점이다. 외부에 위치한 파일을 서버 측 처리에 포함하면서 정보 노출이나 코드 실행으로 이어질 수 있다. 실제 영향은 사용 언어와 설정에 따라 달라진다.

### 6) LFI

LFI(Local File Inclusion)는 서버에 있는 로컬 파일을 의도치 않게 포함하는 취약점이다. 파일 경로에 대한 통제가 부족하면 민감한 파일의 내용이 노출될 수 있으며, 조건에 따라 코드 실행으로 이어질 수도 있다.

RFI와의 차이는 대상 파일의 위치이다. LFI가 항상 악성 스크립트 실행으로 이어지는 것은 아니다.

## 4. 웹 취약점 대응 방안

### 1) Brute Force 대응

**로그인 재시도 제한과 지연**

비정상적인 로그인 실패가 반복되면 재시도 간격을 늘리거나 일시적으로 제한하는 기능을 적용한다. IP 기준뿐 아니라 계정 기준의 시도 횟수도 살펴야 한다. 계정 잠금 기능 자체가 정상 사용자의 접속을 막는 데 악용되지 않도록 설계해야 한다.

**강한 비밀번호와 추가 인증**

충분히 길고 예측하기 어려운 비밀번호를 사용하도록 하고, 흔하거나 유출된 비밀번호를 피하도록 한다. 대문자나 특수문자를 포함했다는 이유만으로 안전성을 보장할 수는 없다. 다중요소 인증도 함께 적용할 수 있다.

**위험 징후에 따른 비밀번호 변경**

유출이나 계정 탈취가 의심되는 경우 비밀번호 변경과 세션 종료 등의 보호조치를 수행한다. 단순한 주기적 변경만으로 반복 공격을 막을 수 있는 것은 아니다.

### 2) SQL Injection 대응

**입력값 검증과 파라미터 바인딩**

입력값이 예상한 형식과 범위를 따르는지 검증한다. SQL 쿼리에는 준비된 문장(prepared statement)과 파라미터 바인딩을 사용하여 입력값이 SQL 코드로 해석되지 않도록 한다.

**안전한 저장 프로시저 사용**

저장 프로시저를 사용하더라도 내부에서 입력을 문자열로 이어 붙여 동적 SQL을 만들면 취약점이 남을 수 있다. 저장 프로시저 자체보다 안전한 쿼리 구성 방식이 중요하다.

**서버와 데이터베이스의 권한 제한**

데이터베이스 계정에는 필요한 최소 권한만 부여한다. 상세 오류 메시지가 외부에 노출되지 않도록 하되, 운영자가 원인을 확인할 수 있는 내부 로그는 유지한다.

### 3) XSS 대응

**입력 형식 제한**

숫자를 받아야 하는 `page`와 같은 값은 숫자와 허용 범위만 받도록 검증한다. 업무상 필요한 입력 형태를 명확히 정의한다.

**출력 문맥에 맞는 인코딩**

HTML 본문, 속성, URL, JavaScript 등 출력되는 위치에 맞는 인코딩을 적용한다. HTML 본문에서 `<script>`를 문자로 보여주려면 `&lt;script&gt;`처럼 인코딩할 수 있지만, 다른 문맥에서는 별도의 처리가 필요하다.

**위험한 스크립트 영역에 출력 자제**

사용자 입력을 이벤트 핸들러나 실행 가능한 JavaScript 영역에 직접 삽입하지 않는다. HTML 입력을 허용해야 하는 경우에는 검증된 정제 기능을 사용한다.

### 4) CSRF 대응

**Origin·Referer 검증**

요청의 Origin 또는 Referer를 확인하여 허용된 출처에서 발생한 요청인지 검증한다. 헤더가 없는 경우의 처리도 명확히 정의해야 하며, 이 검증만으로 모든 공격을 방어한다고 단정해서는 안 된다.

**CSRF 토큰 사용**

세션에 연결된 예측 불가능한 토큰을 발급하고, 상태를 변경하는 요청에서 서버가 토큰을 검증한다. 토큰 검증은 Referer를 사용할 수 없는 경우에만 적용하는 대체 수단이 아니라 주요 방어 방법이다.

**Double Submit Cookie 검증**

쿠키와 요청에 전달된 토큰을 함께 검증하는 방식도 사용할 수 있다. 단순한 값 비교만으로 충분하다고 가정하지 말고, 세션과 연결된 서명 토큰 등 안전한 구현을 선택해야 한다.

쿠키의 SameSite 설정도 보조 방어로 활용할 수 있다. XSS가 있으면 CSRF 방어가 우회될 수 있으므로 두 취약점을 함께 관리해야 한다.

### 5) RFI·LFI 대응

**허용된 파일과 경로만 사용**

사용자 입력을 파일 경로에 직접 사용하지 않도록 한다. 필요한 경우 허용된 식별자를 고정된 파일에 매핑하고, 경로를 정규화한 뒤 허용된 디렉터리 안에 있는지 검증한다. `../`를 단순히 삭제하는 방식만으로는 우회를 막기 어렵다.

**불필요한 원격 파일 포함 기능 비활성화**

PHP 등 사용 환경에서 원격 파일 포함 기능이 필요하지 않다면 비활성화한다. 원격 포함 제한만으로 로컬 파일 포함 취약점까지 해결되는 것은 아니다.

**상세 오류 노출 제한**

외부 사용자에게 서버 경로나 설정 등이 포함된 상세 오류를 보여주지 않는다. 일반적인 오류 응답을 제공하고 상세 내용은 내부 로그로 남긴다.

## 5. 결론

다양한 운영체제와 브라우저에서 금융 서비스를 이용할 수 있도록 하는 것은 접근성과 편의성을 높이는 중요한 변화이다. 당시 조사에서는 Linux를 지원하지 않거나 이용이 불안정한 서비스도 있어 호환성 개선의 필요성을 확인할 수 있었다.

금융 서비스는 민감한 개인정보와 거래를 처리하므로 웹 애플리케이션의 취약점을 지속적으로 점검해야 한다. 운영체제 지원 확대와 함께 인증·권한 관리, 안전한 입력·출력 처리, 데이터베이스와 파일 접근 통제 등 기본적인 보안을 갖추는 것이 중요하다.
